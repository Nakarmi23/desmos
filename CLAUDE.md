## Working in `packages/db-core`

Entry point is `src/index.ts` → `raw-table-to-knex-table.ts` → `raw-column-to-knex-column.ts` /
`raw-constraint-to-knex-constraint.ts`, with the schema vocabulary (`DBTable`, `DBColumn`,
`DBConstraint`, ...) in `src/types/`. Read those directly for how a `DBTable` lowers to Knex builder
calls — the source is small.

Run scripts via `pnpm --filter @repo/db-core <script>` from the root, or from inside the package
(see its `package.json` for the full list):

- Run a single test file: `pnpm test raw-column-to-knex-column.test.ts`.
- Run a single test by name: `pnpm test -t "test name substring"`.

Gotchas that aren't obvious from a quick read:

- In `raw-column-to-knex-column.ts`, `column.name` (used for `foreign()`/`primary()`) is passed
  *un*-snake-cased, while the `specificType()` call uses the snake_cased name. This asymmetry is
  intentional given current tests — don't "fix" it without checking.
- `DBClient` support is mostly aspirational: most logic (the `specificType` DDL strings,
  `gen_random_uuid()`) is Postgres-specific. `uuidDefault` in `id-defaults.ts` picks its default via
  the `DB_CLIENT` env var, defaulting to postgres.
- Tests never touch a real Knex instance — `src/utilities/test-helpers.ts` provides chainable
  Jest-mock stand-ins for `Knex.SchemaBuilder`/`TableBuilder`/foreign-key builder, exposing
  `_tableBuilder`/`_foreignBuilder` so assertions can check exact builder calls instead of executing
  SQL. `pg` + docker-compose exist for integration testing but aren't used by the current suite.
